Ceph RBD·CephFS·RGW 인터페이스별 풀 차이와 쓰기가 OSD에 저장되는 과정

S3 쪽 부하가 RBD 위 DB 쓰기를 늦춘 이유를, RBD·CephFS·RGW 쓰기가 풀·PG·OSD를 거치는 ①~⑩ 단계로 따라간다.

①~⑤ RBD⑥~⑩ CephFS·RGW생기는 결과점검 순서

S3 데이터 풀 재배치가 돌던 주에, 같은 클러스터의 PostgreSQL 쿼리가 10초 타임아웃을 넘기 시작했고 워크플로 작업이 5일 20시간 동안 한 건도 끝나지 않았다. DB는 RBD 볼륨이고 S3는 RGW 버킷이라 서로 다른 스토리지다. S3 쪽 작업이 왜 DB를 멈췄을까?

정답부터 말하면 RBD·CephFS·RGW는 입구만 다르고, 쓰기는 모두 같은 OSD(디스크)에 RADOS 객체로 떨어진다. RBD 쓰기는 복제본이 모두 디스크에 써져야 끝나서, 그중 한 디스크가 S3 작은 객체와 재배치로 바쁘면 DB 쓰기도 그만큼 기다린다.

그럼 세 입구는 어디서 갈리고 어디서 합쳐질까? DB 볼륨 쓰기(①~⑤), 공유 디렉터리 파일 쓰기(⑥~⑦), S3 PUT(⑧~⑩)을 따라가고, 갈리는 지점인 풀 설정(size·failureDomain·device class)에서 생긴 결과를 그 뒤에 모았다.

1. RBD: DB 볼륨 쓰기 한 번이 OSD 세 개에 저장되기까지

① StorageClass ceph-block으로 PVC를 만들면 Rook CSI가 ceph-blockpool에 RBD 이미지를 만듦

$ rbd info ceph-blockpool/csi-vol-<uuid>     # 10 GiB PVC
size 10 GiB in 2560 objects
order 22 (4 MiB objects)
features: layering

→ 10 GiB 이미지는 4 MiB 객체 2,560개(10 GiB ÷ 4 MiB)로 나뉘어 풀에 저장된다. 객체는 데이터가 쓰인 자리만 실제로 만들어진다.

② 노드에 블록 장치로 붙고, 그 위 ext4에 DB가 씀

$ kubectl get pvc -A
# STORAGECLASS·ACCESS MODES 열을 세면
#   ceph-block  RWO  42개   PostgreSQL·MongoDB·TimescaleDB 등 DB, Kafka 브로커, Prometheus

→ ext4는 한 노드만 마운트한다고 가정하는 파일시스템이라, Rook CSI는 파일시스템 모드 RBD 볼륨에 한 노드 접근 모드(ReadWriteOnce)만 허용한다. 노드 단위라 같은 노드에 뜬 파드 여럿은 한 볼륨을 같이 쓸 수 있다.

→ 다른 노드에 이미 붙은 RWO 볼륨을 두 번째 노드의 파드가 쓰려 하면 Multi-Attach 오류로 기동하지 못하고, 처음부터 ReadWriteMany로 요청하면 ceph-csi가 거부해 PVC가 만들어지지 않는다(쿠버네티스·ceph-csi 문서 기준).

→ 파일 이름·디렉터리는 ext4가 블록 안에 적는다. 그래서 RBD에는 Ceph가 따로 지킬 메타데이터 풀이 없다.

③ DB가 쓴 위치가 객체 하나로, 객체 이름이 PG 하나로 정해짐

rbd_data.<이미지 id>.<객체 번호 16진수 16자리>   # 객체 번호 = 쓴 위치 ÷ 4 MiB (Ceph 이름 형식)
$ ceph osd map ceph-blockpool rbd_data.<이미지 id>.0000000000000000   # 객체가 갈 PG와 OSD (출력 형식)
osdmap e<epoch> pool 'ceph-blockpool' (<풀 번호>) object 'rbd_data.<이미지 id>.0000000000000000' -> pg <풀 번호>.<객체 해시 8자리> (<풀 번호>.<PG 번호>) -> up ([<osd>,<osd>,<osd>], p<osd>) acting ([<osd>,<osd>,<osd>], p<osd>)

→ 객체 이름 해시를 풀의 PG 수로 나눈 나머지가 괄호 안 PG 번호다. ceph-blockpool은 PG가 32개라, DB 볼륨의 모든 객체가 이 32개 중 하나에 들어간다.

④ CRUSH 규칙이 PG 복제본 세 벌을 놓을 OSD를 고름

cephBlockPools:
  - name: ceph-blockpool
    spec:
      failureDomain: osd     # 복제본을 서로 다른 디스크에 (노드는 같아도 됨)
      replicated:
        size: 3

→ failureDomain: osd는 디스크만 다르면 된다. 노드 3대에 OSD 4개씩인 클러스터에서 블록 풀 PG 32개의 복제본이 몇 개 노드에 걸쳤는지 세면 이렇다(세는 명령은 3장).

복제본 3벌이 걸친 노드 수PG 수 (클러스터 두 곳)
1개1
2개22~23
3개8~9

→ 두 클러스터 모두 PG 하나는 세 벌이 한 노드에 있다.

⑤ primary OSD가 나머지 두 OSD에 복제하고, 세 벌이 다 써져야 완료를 돌려줌

  1. 노드의 RBD 드라이버는 ③ 출력의 acting 목록(이 PG를 지금 맡은 OSD들) 가운데 primary(p<osd>)에만 쓴다(⑤는 Ceph 문서 기준).
  2. primary가 같은 쓰기를 나머지 두 OSD에 보낸다.
  3. 세 OSD가 모두 디스크에 쓴 뒤 primary가 완료를 돌려준다.

→ RBD 쓰기 지연은 세 디스크 중 가장 늦은 디스크가 정한다. 그 디스크를 다른 풀이 바쁘게 쓰고 있으면 DB 쓰기도 그만큼 기다린다.

2. CephFS·RGW: 파일 쓰기와 S3 PUT이 메타데이터 풀을 따로 거치기까지

⑥ 공유 디렉터리 파드가 파일을 열면 MDS가 메타데이터 풀에서 이름·권한을 찾음

$ kubectl get pvc -A
#   ceph-filesystem  RWX  7개   이미지 레지스트리 저장소, Kafka Connect 플러그인 jar, 워크플로 DAG·로그 공유 디렉터리

→ 여러 노드의 파드가 같은 파일을 봐야 해서 접근 모드가 ReadWriteMany다.

→ CephFS는 파일 이름·디렉터리·권한을 메타데이터 서버 MDS가 관리하고 메타데이터 풀(ceph-filesystem-metadata)에 저장한다. 메타데이터 풀 실데이터는 570 MiB였다.

⑦ 파일 내용은 클라이언트가 데이터 풀 객체로 OSD에 직접 씀

→ MDS를 거치는 것은 이름과 권한이다. 파일 내용은 데이터 풀(ceph-filesystem-data0, 실데이터 47 GiB)의 객체가 되어 ③~⑤와 같은 순서로 OSD에 간다(Ceph 문서 기준).

→ 메타데이터 풀은 데이터 풀보다 훨씬 작지만, 잃으면 데이터 풀이 정상이어도 파일 이름과 디렉터리 구조가 사라진다.

⑧ 앱이 S3 PUT을 HTTP로 RGW에 보냄

PUT /<버킷>/<객체 키>     # 파이프라인 앱이 센서 원본·전처리 결과 파일을 통째로 올림

→ S3 API에는 객체 일부만 고쳐 쓰는 호출이 없다. PUT으로 통째 쓰고 GET으로 통째 읽는다. 볼륨을 붙이지 않으니 접근하는 노드 수에 제한이 없다.

→ 같은 RGW에 로그 저장소 Loki와 테이블 포맷 Iceberg도 각자 버킷을 둔다. 그래서 dataPool의 size를 바꾸면 이 버킷들도 함께 2벌이 된다.

⑨ RGW가 객체 내용을 rgw.buckets.data 풀에 씀

→ 여기부터는 ③~⑤와 같다. 객체 이름 해시로 PG가, CRUSH 규칙으로 OSD가 정해진다.

→ 파일이 작으면 크기에 비해 디스크 입출력 횟수가 많다. 첫 문단의 장애가 난 클러스터의 데이터 풀에는 평균 51 KiB 객체가 6.9억 개 있었다.

⑩ RGW가 버킷 index 샤드의 omap에 객체 키를 추가함

→ RGW는 버킷마다 index를 샤드로 나눠 rgw.buckets.index 풀 객체의 키-값 저장소(omap)에 둔다. 객체 키의 해시로 샤드가 정해진다. 실제로는 객체 head를 쓰기 직전에 index에 쓰기 예정 항목을 먼저 적고, head를 쓴 뒤 확정한다. 51 KiB처럼 작은 객체는 내용 전체가 head에 들어가서 index 기록이 ⑨보다 먼저다(Ceph 소스 기준).

→ 객체 1,697만 개가 든 버킷은 샤드가 197개였고, 샤드 하나에 평균 약 8.6만 키(1,697만 ÷ 197)가 있었다.

→ Ceph는 deep scrub 때 omap 키 수가 osd_deep_scrub_large_omap_object_key_threshold(기본값 200,000)를 넘는 객체가 있으면 LARGE_OMAP_OBJECTS 경고를 낸다. 첫 문단의 클러스터에는 이 경고가 413개 떠 있었다.

→ index 풀(실데이터 2.7 GiB)을 잃으면 데이터 풀에 객체 내용이 있어도 버킷에서 찾을 수 없다.

①~⑩을 풀 기준으로 모으면 이렇다.

인터페이스쓰기가 거치는 풀동시에 쓰는 노드따로 지킬 메타데이터 풀규모
RBDceph-blockpool1개 (RWO)없음 (ext4가 블록 안에 기록)PVC 42개
CephFSceph-filesystem-metadata, ceph-filesystem-data0여러 개 (RWX)메타데이터 풀 + MDS실데이터 570 MiB / 47 GiB
RGWceph-objectstore.rgw.* 메타데이터 풀 7개, rgw.buckets.data제한 없음index 풀실데이터 index 2.7 GiB / 데이터 38 TiB

3. Rook values의 size·failureDomain과 같은 HDD에서 생기는 결과

①~⑩에서 인터페이스마다 쓰기가 다른 풀을 거치는 것을 봤다. 이번에 본 클러스터들은 이 풀들이 모두 같은 OSD 12개를 쓴다. Rook values는 그 풀마다 줄을 따로 둔다. 설정에서 복제 수와 배치 규칙 줄만 남기면 이렇다.

cephBlockPools:              # ①~⑤ ceph-blockpool
  - name: ceph-blockpool
    spec:
      failureDomain: osd
      replicated:
        size: 3
cephFileSystems:
  - name: ceph-filesystem
    spec:
      metadataPool:          # ⑥ ceph-filesystem-metadata
        replicated:
          size: 3
      dataPools:             # ⑦ ceph-filesystem-data0
        - failureDomain: osd
          replicated:
            size: 3
cephObjectStores:
  - name: ceph-objectstore
    spec:
      metadataPool:          # ⑩ index를 포함한 RGW 메타데이터 풀 7개가 이 한 줄을 같이 씀
        failureDomain: host
        replicated:
          size: 3
      dataPool:              # ⑨ rgw.buckets.data — S3 공간을 회수할 때 고치는 줄
        failureDomain: host
        replicated:
          size: 3

→ RBD는 풀 하나, CephFS와 RGW는 메타데이터 풀과 데이터 풀을 따로 써서 size: 줄이 1 + 2 + 2 = 5개다. S3 데이터의 복제 수만 줄이려면 cephObjectStores의 dataPool 줄을 고친다. 바로 위 metadataPool 줄은 ⑩의 index를 포함한 RGW 메타데이터 풀 7개를 한꺼번에 바꾼다.

metadataPool의 size를 바꾸면 ⑩의 index 풀을 포함한 7개 풀의 복제 수가 함께 바뀜

  1. 디스크 사용률이 89.76%인 클러스터에서 S3 데이터를 2벌로 줄이려다, dataPool 줄 대신 metadataPool 줄을 잘못 2로 저장했다.
  2. RGW 메타데이터 풀 7개가 2벌이 됐다. 이 풀들은 합쳐 3 GiB 미만이라 공간은 거의 비지 않는다.
  3. 1분 만에 3으로 되돌렸다 → 그사이 지워진 세 번째 복제본을 다시 만들어야 해서, index 등 PG 18개가 복제본이 모자란 undersized+degraded가 됐다.
  4. 그중 11개는 일부 OSD 사용률이 backfillfull 비율(93%)을 넘어 backfill_toofull로 대기했다 → 되돌린 뒤 약 14분 만에(19:57 → 20:11) undersized·degraded PG가 0이 됐다.

→ 공간 회수는 dataPool 줄로만 한다. 데이터 풀을 3벌에서 2벌로 줄이면 복제본 한 벌만큼(실데이터 38 TiB × 1벌) 빌 것으로 계산된다.

dataPool의 size를 2로 바꾸면 PG autoscaler가 목표 PG를 128에서 512로 올림

  1. autoscaler는 OSD 하나당 PG 100개(mon_target_pg_per_osd)를 목표로 "풀이 차지한 디스크 비율 × OSD 수 × 100 ÷ 복제 수"를 계산해 가까운 2의 거듭제곱으로 맞추고, 현재 값과 3배 이상 차이 날 때만 바꾼다(Ceph 문서 기준).
  2. 바꾸기 전: 0.866(ceph osd pool autoscale-status의 RATIO, 원시 사용량 약 113 TiB ÷ 전체 131 TiB) × 1,200(OSD 12개 × 100) ÷ 3 ≈ 346 → 256. 현재 128과 2배 차이라 그대로였다.
  3. 바꾼 직후: 세 번째 복제본이 아직 지워지지 않아 비율은 그대로인데 나누는 수만 2가 됐다 → 0.866 × 1,200 ÷ 2 ≈ 520 → 512. 128과 4배 차이라 PG 분할이 시작됐다.
  4. ③처럼 객체가 들어갈 PG는 이름 해시를 PG 수로 나눈 나머지다 → PG가 128개에서 512개로 쪼개지면 객체 대부분이 새 PG로 나뉘고, pgp_num이 따라 오르면 ④의 CRUSH가 새 PG마다 OSD를 다시 고른다.
  5. 그래서 Ceph 명령을 실행하는 toolbox 파드(rook-ceph-tools)에서 autoscale을 끄고 목표를 128로 되돌렸다.
# rook-ceph-tools 파드 안에서 실행
$ ceph osd pool set ceph-objectstore.rgw.buckets.data pg_autoscale_mode off
$ ceph osd pool set ceph-objectstore.rgw.buckets.data pg_num 128
$ ceph osd pool ls detail | grep buckets.data
pool 12 'ceph-objectstore.rgw.buckets.data' replicated size 2 min_size 1 ... pg_num 252 pgp_num 135 pg_num_target 128 pgp_num_target 128 autoscale_mode off ...

→ pg_num은 PG 개수이고, 데이터를 실제로 옮기는 기준은 pgp_num이다. 되돌린 시점에 pgp_num은 135까지만 올라가 있어 배치가 바뀐 PG는 7개였다.

→ 복제본이 다 지워지면 계산값은 약 0.58(약 76 TiB ÷ 131 TiB) × 1,200 ÷ 2 ≈ 348 → 256으로 돌아올 것으로 계산된다. 하지만 한 번 정해진 512와는 3배 미만 차이라 목표가 내려가지 않을 것으로 봤다(3배 규칙 기준 예상).

→ toolbox에서 끈 값은 Rook이 풀을 다시 맞출 때 바뀔 수 있어 values에도 넣는다(아직 반영 전).

      dataPool:
        failureDomain: host
        replicated:
          size: 2
        parameters:
          pg_autoscale_mode: "off"   # Rook이 풀을 재조정할 때 이 값으로 맞춘다

블록 풀이 failureDomain: osd면 PG 하나의 세 벌이 노드 한 대에 모임

  1. ④처럼 osd 규칙은 디스크만 다르면 된다 → 두 클러스터 모두 PG 32개 중 1개는 세 벌이 한 노드에, 22~23개는 두 노드에만 있었다.
  2. 두 클러스터의 블록 풀은 min_size 1이다 → 노드 한 대가 꺼지면 두 노드에만 걸친 PG 일부는 1벌만 남은 채 쓰기를 계속 받고, 그 1벌이 있는 디스크까지 고장 나면 그사이 쓴 데이터를 잃는다.
  3. 세 벌이 한 노드에 있던 PG는 그 노드가 돌아올 때까지 입출력이 멈춘다 → 그 노드 디스크까지 잃으면 그 PG에 든 DB 볼륨 객체는 복구할 곳이 없다.
# rook-ceph-tools 파드 안에서 실행: acting set의 OSD를 osd tree의 host로 바꿔 PG마다 서로 다른 host 수를 센다
cd /tmp
ceph osd tree -f json > tree.json
ceph pg ls-by-pool ceph-blockpool -f json > pgs.json
python3 - <<'EOF'
import json, collections
host = {c: n["name"] for n in json.load(open("tree.json"))["nodes"] if n["type"] == "host" for c in n.get("children", [])}
pgs = json.load(open("pgs.json"))["pg_stats"]
print(collections.Counter(len({host[o] for o in p["acting"]}) for p in pgs))
EOF

→ Rook 차트 기본값은 블록·CephFS·RGW 풀 모두 host다. 이번에 본 클러스터들의 값은 3노드 배포 템플릿과 같아, 그 템플릿이 블록 풀과 CephFS 데이터 풀만 osd로 지정한 것이 인터페이스마다 값이 갈린 이유로 보인다.

values의 failureDomain을 host로 바꿔도 Rook 1.17.2는 기존 풀의 CRUSH 규칙을 바꾸지 않았음

  1. values의 CephFS 데이터 풀 failureDomain을 host로 바꿨다.
  2. operator 로그에는 "reconciling replicated pool … succeeded"만 남고, 풀의 규칙은 osd 그대로였다.
  3. 그래서 Ceph에서 노드 단위 규칙을 직접 만들어 풀에 연결했다.
# rook-ceph-tools 파드 안에서 실행 (CephFS 데이터 풀 사례)
ceph osd crush rule create-replicated data0-host default host
ceph osd pool set ceph-filesystem-data0 crush_rule data0-host
# 이후 operator 재기동으로 되돌림이 없음을 확인하고, 원래 규칙 이름(ceph-filesystem-data0)을 host로 다시 만들어 연결한 뒤 임시 규칙 삭제

→ 블록 풀도 같은 방식으로 바꿀 예정이다. 옮길 PG는 한 클러스터 기준 23개이고, 그 PG들의 복제본 1벌 크기 합은 1.66 TiB다. 복제 수만큼 노드가 있어야 하고(3벌이면 노드 3대), 재배치 중에는 같은 디스크의 DB 지연이 늘 수 있어(예상) 업무 외 시간에 한다.

같은 HDD를 RGW 작은 객체와 PG 재배치가 채우면 ⑤의 RBD 쓰기 대기가 늘어남

  1. 첫 문단의 클러스터는 OSD 12개가 모두 HDD였고, OSD 내부 DB(RocksDB)와 쓰기 로그(WAL)도 같은 HDD에 있었다. 세 인터페이스의 풀이 모두 이 12개 디스크를 쓴다.
  2. ⑨의 평균 51 KiB 객체 6.9억 개 때문에, 처리량이 낮을 때도 디스크 사용률이 50~80%였다.
  3. 데이터 풀 pgp_num을 63에서 128로 한 번에 올렸다 → 객체 복제본의 40%(6.9억 개 × 2벌 × 0.4 ≈ 5.5억 개)가 제자리를 벗어난 misplaced 상태가 되어 재배치가 시작됐다.
  4. ⑤의 복제본 쓰기(이 클러스터는 블록 풀도 2벌)가 이 디스크를 기다렸다 → 작업 실행을 예약·관리하는 Prefect의 PostgreSQL 볼륨이 있는 노드에서 RBD 쓰기 지연 하루 최댓값이 평소 1~3초에서 최대 58.8초까지 늘었다.
  5. DB 쿼리가 10초 타임아웃을 넘은 시각마다 Prefect 서버가 500을 반환했다 → 제출 중 500을 받은 작업이 실행 대기로 남아 동시 실행 슬롯 20개를 채웠고, 약 5일 20시간 동안 완료된 작업이 0건이었다.

→ 오류 시각 앞뒤 3분의 RBD 쓰기 지연 최댓값은 1.9~14.6초였다. 노드의 RBD 장치 중 최댓값이라, 오류마다 DB 볼륨의 지연이 10초를 넘었다고 볼 수는 없다.

→ 이 클러스터는 동시 재배치 수 osd_max_backfills 1, 클라이언트 요청을 우선하는 osd_mclock_profile high_client_ops 상태였는데도 지연이 났다. HDD만 있으면 나눌 디스크가 없어서, pgp_num처럼 대량 이동을 부르는 값을 한 번에 크게 바꾸지 않고 업무 외 시간에 나눠 바꾸는 방법이 남는다.

→ 복제 수를 3에서 2로 줄인 클러스터에서는 재복제·재배치가 도는 동안 OSD 6개에서 BLUESTORE_SLOW_OP_ALERT(디스크 작업 지연 경고)가 떴다. 이때 RBD 지연은 재지 않았다.

device class는 블록 풀과 RGW 데이터 풀에 각각 다른 class를 지정해야 디스크가 나뉨

  1. ④의 CRUSH 규칙에 device class(hdd·ssd)를 넣으면 풀이 쓸 디스크 종류를 정할 수 있다.
  2. HDD와 SSD를 섞은 다른 클러스터 한 곳은 블록 풀만 default~hdd 규칙으로 HDD에 묶고, RGW 데이터 풀은 모든 디스크를 쓰게 뒀다.
  3. RGW 데이터 풀도 HDD를 쓴다 → RGW 부하가 같은 HDD를 거쳐 블록 풀 지연으로 이어질 수 있는 구조였다(지연은 측정하지 않음).

→ 규칙을 host로 바꿀 때 class까지 한 규칙에 넣으면(ceph osd crush rule create-replicated <규칙> default host <class>) 노드 단위와 디스크 종류가 한 번의 재배치로 바뀐다. 따로 바꾸면 같은 데이터가 두 번 재배치된다.

values와 라이브 풀의 size가 다르면 ArgoCD가 CR을, Rook이 풀을 values 쪽으로 되돌림

  1. values의 데이터 풀 size는 3인데 라이브 풀만 2로 바꿔 둔 클러스터가 있었다.
  2. 차트 저장소 자격 증명 만료로 멈춰 있던 ArgoCD 동기화가 복구됐다 → ArgoCD가 CR을 values로, Rook operator가 풀을 CR로 되돌려 3이 됐고 backfill_toofull이 났다.

4. Ceph 풀 문제는 풀별 size·autoscale·규칙 type·device class 순서로 확인

  1. 복제 수가 예상과 다르거나 바꾼 값이 되돌아간다 → ceph osd pool ls detail로 풀마다 size를 보고 values와 대조한다. 다르면 ArgoCD selfHeal이 CR을 values로, Rook operator가 풀을 CR로 되돌린다.
  2. 복제 수를 바꾼 뒤 PG 수가 늘기 시작한다 → 같은 출력의 pg_num_target·autoscale_mode를 본다. 공간 회수 전에 values dataPool.parameters에 pg_autoscale_mode: "off"를 넣는다.
  3. 노드 한 대가 꺼졌을 때 멈추는 PG가 있다 → ceph osd crush rule dump에서 블록 풀 규칙의 type이 host인지 본다. osd면 3장 명령으로 PG를 세고, 규칙을 직접 만들어 풀에 연결한다.
  4. DB 지연이 S3 부하와 같이 움직인다 → 블록 풀과 RGW 데이터 풀 규칙의 device class가 같은지 본다. 같으면 재배치·pgp_num 변경 시각과 지연 시각을 맞춰 본다.
