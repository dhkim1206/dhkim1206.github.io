kubelet은 ConfigMap 변경을 언제 파드에 넣는가

env·envFrom·볼륨·items·subPath 다섯 주입 방식의 반영 시점과 이름 중복·키 이름·immutable 동작을 실측한 기록입니다.

ConfigMap은 맞았던 사례다섯 경로 구성볼륨·items만 자동 반영rollout restart env 이름 중복1key 환경변수immutable방식별 판정확인하지 못한 것맺음말

ConfigMap은 맞았는데 파드에 넣는 방식 때문에 세 번 문제를 겪었다

데이터 파이프라인을 운영하면서 겪은 세 사례입니다.

  • Kafka에서 메시지를 받아 처리하는 컨슈머 서비스의 설정을 바꿀 때, 조치 절차에 ConfigMap 수정 뒤 kubectl rollout restart를 함께 넣어야 했습니다. 이 서비스는 설정을 envFrom으로 받습니다.
  • 같은 이름의 환경변수를 Helm 차트 템플릿과 values가 둘 다 만들어, Git의 매니페스트와 클러스터 상태를 맞추는 ArgoCD가 두 상태를 비교하지 못했다는 ComparisonError로 5번 재시도한 끝에 sync를 멈췄습니다.
  • ConfigMap에 든 S3 접속 키는 맞는데 Secret을 가리키는 deployment의 env가 그 값을 덮어, 파드가 다른 접속 키를 쓰고 있었습니다(지난 글).

세 번 모두 ConfigMap 자체는 맞았고, 달랐던 것은 그 값을 파드에 넣은 방식이었습니다. ConfigMap을 고치고 GitOps 도구가 Synced를 보여 줘도, 넣은 방식에 따라 파드는 옛 값을 계속 쓸 수 있습니다. ConfigMap을 고친 뒤 파드가 새 값을 쓰는지 어떻게 확인하고 계신가요?

ConfigMap 값을 파드에 넣는 방식은 다섯 가지이고, 방식마다 반영 시점과 이름이 겹쳤을 때의 동작이 다릅니다.

같은 키를 env·envFrom·볼륨·items·subPath 다섯 경로로 한 파드에 넣었다

Docker 컨테이너를 노드로 쓰는 로컬 클러스터 도구 kind로 Kubernetes v1.37 클러스터를 띄우고, ConfigMap app-config(키 GREETING)의 키를 다섯 경로로 한 컨테이너에 넣었습니다.

containers:
  - name: probe
    image: busybox:1.36
    env:
      - name: GREETING_ENV                 # ① env — 키 하나를 이름을 정해 환경변수로
        valueFrom:
          configMapKeyRef: {name: app-config, key: GREETING}
    envFrom:
      - configMapRef: {name: app-config}   # ② envFrom — 키 전부를 이름 그대로 환경변수로
    volumeMounts:
      - {name: full,  mountPath: /cfg-full}                              # ③ 볼륨 전체 — 키마다 파일 하나
      - {name: items, mountPath: /cfg-items}                             # ④ 볼륨 items — 고른 키만 지정한 파일명으로
      - {name: full,  mountPath: /cfg-sub/greeting, subPath: GREETING}   # ⑤ subPath — 파일 하나를 특정 경로에
volumes:
  - name: full
    configMap: {name: app-config}
  - name: items
    configMap:
      name: app-config
      items: [{key: GREETING, path: greeting.txt}]

컨테이너는 1초마다 다섯 경로의 값을 한 줄로 찍습니다. 처음에는 다섯 경로 모두 v1이었습니다.

1791651653 env=v1 envfrom=v1 full=v1 items=v1 subpath=v1

볼륨 전체와 items로 넣은 값만 64~71초 뒤 바뀌었고, env·envFrom·subPath는 150초 동안 그대로였다

kubectl patch로 GREETING을 바꾼 시각부터 150초 동안 로그를 1초 간격으로 보며, 각 경로가 새 값을 보인 시점을 3회 쟀습니다.

변경① env② envFrom③ 볼륨 전체④ 볼륨 items⑤ subPath
v1 → v2150초 동안 그대로150초 동안 그대로71초71초150초 동안 그대로
v2 → v3150초 동안 그대로150초 동안 그대로68초68초150초 동안 그대로
v3 → v4150초 동안 그대로150초 동안 그대로64초64초150초 동안 그대로

볼륨 쪽은 공식 문서가 설명하는 동작과 같습니다. ConfigMap 문서는 볼륨으로 쓰는 ConfigMap이 바뀌면 파일도 결국 바뀐다고 하면서, 그 지연이 "kubelet sync period + cache propagation delay"까지 걸릴 수 있다고 적습니다. 노드에서 파드를 실행하고 볼륨 파일을 채우는 kubelet의 설정을 꺼내 보니, 동기화 주기(syncFrequency)는 1분이고 캐시는 apiserver의 변경 알림으로 갱신하는 Watch 방식이었습니다. 1분 주기에 전파 지연이 붙어 64~71초가 나온 것으로 봅니다.

kubectl get --raw /api/v1/nodes/<노드 이름>/proxy/configz   # syncFrequency, configMapAndSecretChangeDetectionStrategy 확인

나머지 셋도 문서에 적힌 그대로입니다. 환경변수로 쓰는 ConfigMap은 "not updated automatically and require a pod restart"이고, subPath로 마운트한 파일은 "will not receive ConfigMap updates"입니다. 환경변수는 컨테이너가 시작할 때 한 번 조립되기 때문입니다. 설정을 envFrom으로 받는 컨슈머 서비스의 조치 절차에 rollout restart가 들어가야 했던 이유가 이것입니다.

볼륨 파일이 바뀌어도 애플리케이션이 그 파일을 다시 읽어야 동작이 바뀝니다. 시작할 때 한 번만 설정 파일을 읽는 애플리케이션이라면 볼륨으로 넣어도 재시작해야 합니다.

rollout restart 후에는 다섯 경로 모두 새 값이 됐다

kubectl rollout restart deploy/probe로 파드를 새로 띄우자, 새 파드에서는 다섯 경로 모두 마지막 값 v4를 보였습니다.

1791654384 env=v4 envfrom=v4 full=v4 items=v4 subpath=v4

새 컨테이너가 시작하면서 환경변수를 다시 조립하기 때문입니다. subPath는 공식 문서대로 새 컨테이너에서만 새 값을 보였습니다. 그런데 ConfigMap만 바뀌면 deployment의 파드 템플릿은 그대로라 롤링 재시작이 저절로 일어나지 않습니다. GitOps 도구의 Synced만 보고 확인을 끝내면 안 되는 이유가 이것입니다.

Helm 공식 문서는 이 문제를 위해 파드 템플릿 annotation에 ConfigMap 내용의 해시(checksum/config)를 넣는 방법을 안내합니다. ConfigMap 값이 바뀌면 해시가 바뀌고, 파드 템플릿이 바뀌었으니 deployment가 롤링을 합니다(이 방법은 이번 실험에서 재현하지 않았습니다).

spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}

같은 이름의 env는 뒤 항목 값이 들어가고, server-side apply는 거부한다

env에 같은 이름 DUP를 두 번 넣었습니다. 첫 항목은 직접 값, 둘째 항목은 ConfigMap 키입니다.

env:
  - name: DUP
    value: from-value
  - name: DUP
    valueFrom:
      configMapKeyRef: {name: dup-config, key: DUP}   # ConfigMap 값: from-configmap

결과는 이렇습니다(실측). 표의 server-side apply는 apiserver가 env 같은 리스트 항목을 name 키로 맞춰 합치는 apply 방식입니다.

동작결과
kubectl apply (처음)경고 env[1]: hides previous definition of "DUP", which may be dropped when using apply와 함께 생성됨
파드 안 DUPfrom-configmap — 뒤 항목의 값
첫 항목 값만 바꿔 kubectl apply 다시같은 경고와 함께 반영됨
같은 변경을 kubectl apply --server-sideduplicate entries for key [name="DUP"]로 거부

API 서버는 같은 이름을 막지 않고 경고만 남깁니다. 그래서 차트 템플릿과 values가 같은 이름을 각각 만들어도 kubectl apply로는 경고만 나오고 배포되며, server-side apply와 ArgoCD의 diff 계산에서 실패가 드러납니다. ArgoCD에서 본 ComparisonError가 이 경우였는데, 이번 실험의 일반 kubectl apply로는 그 오류 문구까지 재현되지 않았습니다.

같은 이름이 겹쳤는지는 배포 전에 server-side dry-run으로 확인할 수 있습니다. 리소스를 만들지 않고 같은 duplicate entries 오류를 돌려줍니다(dry-run 실측).

helm template <릴리스> <차트> -f values.yaml > rendered.yaml
kubectl apply --server-side --dry-run=server -f rendered.yaml   # 중복이 있으면 env: duplicate entries for key [name="..."]

숫자로 시작하는 키 1key도 v1.32부터 envFrom 환경변수가 된다

ConfigMap에 OK_KEY, my.key, my-key, 1key 네 키를 넣고 envFrom으로 넣었더니, 파드 안에 네 키가 모두 환경변수로 있었고 경고 이벤트도 없었습니다.

1key=digit
OK_KEY=ok
my-key=dash
my.key=dot

이 중 버전에 따라 달라지는 것은 1key 하나이고, my.key·my-key는 게이트 이전 규칙에서도 허용됐습니다. 기능을 버전별로 켜고 끄는 기능 게이트 RelaxedEnvironmentVariableValidation은 1.30에 Alpha(기본 꺼짐)로 들어와 1.32에 Beta(기본 켜짐), 1.34에 GA가 됐습니다. 이 게이트가 꺼진 클러스터(1.31 이하 기본값)의 kubelet은 이름 규칙(영문자·숫자·_·-·., 숫자로 시작하지 않음)에 맞지 않는 키를 건너뛰고 InvalidEnvironmentVariableNames 경고 이벤트를 남깁니다(kubelet 소스 기준, 재현하지 않았습니다).

환경변수가 됐다고 어디서나 쓸 수 있는 것은 아닙니다. 셸 변수 이름 규칙에 맞지 않아 셸 스크립트에서는 $my.key처럼 참조할 수 없고, 애플리케이션이 프로세스 환경을 이름으로 직접 읽을 때만 쓸 수 있습니다.

immutable ConfigMap은 수정 자체를 막는다

immutable: true를 준 ConfigMap의 값을 바꾸려 하면 apiserver가 거부합니다(실측).

The ConfigMap "frozen-config" is invalid: data: Forbidden: field is immutable when `immutable` is set

공식 문서에 따르면 immutable은 되돌릴 수 없어, 값을 바꾸려면 ConfigMap을 지우고 다시 만들어야 합니다. 기존 파드는 지운 ConfigMap을 계속 마운트하고 있으므로 파드도 다시 만드는 것이 권장됩니다. 문서는 쓰임새로 실수로 값이 바뀌어 생기는 장애를 막는 것과, immutable ConfigMap의 watch를 닫아 apiserver 부하를 줄이는 것을 듭니다. 값을 바꿔야 할 때는 이름에 버전을 넣은 새 ConfigMap(app-config-v2)을 만들고 deployment가 그 이름을 가리키게 바꾸는 방법이 있습니다.

방식별 판정과 상황별 선택

방식ConfigMap을 바꾸면파드 값의 출처 추적같은 이름이 겹치면
① env configMapKeyRef150초 내 미반영, 재시작 후 반영 (실측)spec에 변수 이름과 키가 1:1로 적혀 있음env끼리는 뒤 항목 값이 들어가고 경고, server-side apply는 거부 (실측)
② envFrom150초 내 미반영, 재시작 후 반영 (실측)spec에는 ConfigMap 이름만 있어 키 목록을 같이 봐야 함목록 뒤쪽 소스가 남고(API 설명), 같은 이름의 env에 덮임(지난 글 실측)
③ 볼륨 전체64~71초 뒤 반영 (실측)파일 이름이 키키마다 파일이라 겹치지 않음
④ 볼륨 items64~71초 뒤 반영 (실측)지정한 파일 경로겹치지 않음
⑤ subPath150초 내 미반영, 재시작 후 반영 (실측)지정한 파일 하나겹치지 않음

상황별로 고르면 이렇습니다.

상황맞는 방식감수할 것
값을 바꾸면 재시작 없이 반영돼야 하고, 애플리케이션이 파일을 다시 읽는다③ 볼륨 전체 또는 ④ items이번 측정 64~71초 지연, 파일을 다시 읽는 코드
설정 파일 하나를 정해진 경로에 둬야 한다④ items (⑤ subPath 대신)디렉터리 단위로 마운트되어 그 디렉터리의 기존 파일이 가려짐
값은 시작할 때 한 번만 필요하고, 바꿀 때는 배포로 바꾼다① env 또는 ② envFrom + checksum/config annotation바뀔 때마다 롤링 재시작
파드 값의 출처를 spec만 보고 알아야 한다① env키마다 한 줄씩 적어야 함
값이 바뀌면 안 된다immutable + 이름에 버전바꿀 때 새 ConfigMap과 deployment 수정

확인하지 못한 것

  • 애플리케이션이 바뀐 파일을 다시 읽는지는 애플리케이션마다 다릅니다. 이 실험은 매초 cat으로 읽었습니다.
  • 1.31 이하 클러스터에서 envFrom이 1key 같은 키를 건너뛰는 동작은 kubelet 소스(release-1.29) 기준이고 재현하지 않았습니다.
  • ArgoCD의 ComparisonError 문구는 일반 kubectl apply로 재현되지 않았습니다.
  • 측정은 노드 하나짜리 kind 클러스터에서, 같은 파드로 연속 3회 1초 단위로 했습니다. 노드가 많거나 apiserver 부하가 큰 클러스터에서는 지연 분포가 다를 수 있습니다.

같은 측정은 위 YAML로 파드를 띄운 뒤 아래 명령으로 재현할 수 있습니다.

kubectl patch configmap app-config --type merge -p '{"data":{"GREETING":"v2"}}'   # 실행 시각부터
kubectl logs -f deploy/probe                                                         # 각 경로 값이 바뀌는 시각을 본다

맺음말

ConfigMap을 바꿨을 때 재시작 없이 바뀐 것은 볼륨 전체·items로 넣은 값뿐이었고, 그것도 kubelet 동기화 주기(1분)에 전파 지연을 더한 만큼 늦게 바뀌었습니다(이번 측정 64~71초).

환경변수와 subPath는 컨테이너가 다시 시작해야 바뀌고, GitOps의 Synced는 ConfigMap이 클러스터에 적용됐다는 것까지만 알려 줍니다. 같은 이름의 환경변수가 겹치면 server-side dry-run이 duplicate entries 오류를 돌려주므로, ComparisonError로 이어진 그 중복도 배포 전에 잡을 수 있었을 것이고, env가 envFrom 값을 덮는 경우는 아래 셋째 확인에서 드러납니다. ConfigMap을 고친 뒤에는 이 순서로 확인합니다.

  1. 그 값이 어떤 방식으로 파드에 들어가는지 deployment에서 확인합니다.
  2. 환경변수·subPath라면 롤링 재시작이 일어났는지(파드 생성 시각) 확인합니다.
  3. 파드 안에서 실제 값을 꺼내 ConfigMap 값과 비교합니다.
