Kong OIDC 플러그인과 Keycloak 로그인에서 요청마다 오가는 쿠키·토큰·헤더

백엔드가 받는 X-Credential-Identifier가 어디서 오는지, 첫 요청 302부터 API 헤더까지 ①~⑪ 단계로 따라간다.

①~⑧ 로그인⑨~⑪ API 호출생기는 결과점검 순서

Kong 뒤 백엔드 로그에 찍히는 X-Credential-Identifier: 3f2a1c… 이게 뭘까?

정답부터 말하면 Keycloak 사용자 UUID(ID 토큰의 sub)이고, 백엔드가 아니라 Kong의 OIDC 플러그인(oidcify)이 요청마다 넣어 주는 헤더다. 백엔드 코드에 로그인 처리가 없는데도 사용자를 아는 이유가 이것이다.

그럼 Kong은 이 값을 어디서 꺼낼까? 로그인 세션은 Kong 서버에도 Keycloak 서버에도 없고, 브라우저 쿠키 OIDCSESSION0 하나에 암호화돼 있다. Kong은 요청마다 이 쿠키를 풀어 꺼낸다. 브라우저가 이 쿠키를 받기까지(①~⑧)와 그 쿠키로 API를 부르기까지(⑨~⑪)를 차례로 따라가고, 이 구조에서 생기는 결과(Keycloak 장애, 세션 수명, Kong 재시작, 로그아웃)를 그 뒤에 모았다.

플러그인은 오픈소스 Kong 플러그인 oidcify v1.3.2다. ①~③의 응답은 운영 중인 클러스터에서 실제로 받은 것이고, ④부터는 플러그인 소스(main.go)를 따라갔다.

1. 로그인: 쿠키 없는 첫 요청부터 쿠키에 ID 토큰이 들어가기까지

① 브라우저가 쿠키 없이 첫 화면을 요청

curl -s -o /dev/null -D - https://app.example.com/

→ 쿠키가 없으므로 Kong 플러그인은 이 요청을 "로그인 안 된 요청"으로 보고 로그인을 시작한다.

② Kong 플러그인이 로그인을 준비하고 302를 돌려줌

  1. Keycloak 설정 문서에서 로그인 주소와 공개키 주소를 꺼낸다. 5분 캐시에 없으면 Keycloak에서 받는다.
GET https://idp.example.com/realms/product/.well-known/openid-configuration   (예시)
  authorization_endpoint: …/protocol/openid-connect/auth    # 로그인 주소
  jwks_uri:               …/protocol/openid-connect/certs   # 공개키 주소
  1. 로그인을 마친 브라우저가 ⑤에서 돌아오면 Kong이 이 요청이 자기가 보낸 로그인의 응답인지 확인해야 한다. 그 확인에 쓸 값 네 개(state·nonce·PKCE 원본·유효 시각)를 지금 만들어 쿠키에 암호화해 넣는다. 브라우저는 이 내용을 못 읽는다.
State:            1f01f6bf…    ← ⑥에서 돌아온 주소의 state 와 비교. 다르면 남이 보낸 위조 콜백으로 보고 400
Nonce:            95289df8…    ← ⑧에서 ID 토큰 안 nonce 와 비교. 다르면 다른 로그인의 토큰을 재사용한 것으로 보고 500
PKCECodeVerifier: (64자)       ← Keycloak 에는 해시만 먼저 보내고(③), 원본은 ⑥에서 토큰 요청 때 낸다. code 가 새도 원본 없이는 토큰으로 못 바꾼다
ValidUntil:       지금 + 10분  ← ⑥에서 확인. 10분이 지나 돌아오면 400
  1. 브라우저를 Keycloak으로 보내는 302를 돌려준다.

→ Kong 서버에는 아무것도 남지 않는다. ⑥·⑧의 확인에 쓸 값 네 개는 전부 이 쿠키에 있다.

→ 1번에서 Keycloak이 응답하지 않거나 Keycloak 인증서를 신뢰하지 못하면 로그인 주소를 만들 수 없어, 302 대신 500이 나온다.

③ 브라우저가 302를 따라 Keycloak으로 이동

①의 실제 응답이다. 읽기 쉽게 URL 디코딩하고 줄을 나눴다.

HTTP/2 302
location: https://idp.example.com/realms/product/protocol/openid-connect/auth
    ?client_id=app
    &response_type=code
    &scope=openid
    &redirect_uri=https://app.example.com/*   # 로그인 뒤 돌아올 주소. 플러그인 설정값 그대로라 경로도 글자 그대로 /*
    &state=1f01f6bf…        (64자)            # ②에서 쿠키에 넣은 값과 같다
    &nonce=95289df8…        (64자)
    &code_challenge=XI54pq… (43자)            # PKCE 원본의 해시
    &code_challenge_method=S256
set-cookie: OIDCSESSION0=<암호화 780자>; Path=/; HttpOnly; Secure; SameSite=Lax
                                              # 끝 숫자 0은 분할 번호. 4000자를 넘으면 OIDCSESSION1… 최대 10개

→ 주소에는 state·nonce·해시만 실리고 비밀값(client secret, PKCE 원본)은 없다. 비밀값은 ⑥에서 Kong이 Keycloak에 직접 낸다.

④ Keycloak이 비밀번호를 확인하고 1회용 code를 들려 돌려보냄

  1. redirect_uri가 client에 등록된 허용 주소(https://app.example.com/*)와 맞는지 본다.
  2. 로그인 화면을 보여 주고 비밀번호를 확인한다. Keycloak 세션이 이미 있으면 화면 없이 넘어간다.
  3. 자기 도메인(idp.example.com)에 Keycloak 세션 쿠키를 굽는다.
  4. 브라우저를 redirect_uri로 돌려보낸다.
# Keycloak 표준 동작 기준 예시. 실제로는 session_state 등이 더 붙는다
302 location: https://app.example.com/*?state=1f01f6bf…&code=<1회용 코드>

→ 이 주소에도 토큰은 없다. code는 Keycloak 기본값으로 60초 안에 한 번만 쓸 수 있다.

→ 1번에서 주소가 다르면 로그인 화면 대신 Invalid parameter: redirect_uri 오류에서 멈춘다.

⑤ 브라우저가 code를 들고 /* 로 돌아옴

GET https://app.example.com/*?state=1f01f6bf…&code=<1회용 코드>
Cookie: OIDCSESSION0=<암호화{ state·nonce·PKCE 원본·유효 시각 }>

→ 쿠키가 SameSite=Lax라서, 다른 사이트(Keycloak)에서 넘어오는 이 GET 이동에도 쿠키가 실린다.

→ Kong 플러그인은 경로가 설정 redirect_uri의 경로(/*)와 같으면 로그인 콜백으로, logout_path(/logout)와 같으면 로그아웃으로, 나머지는 일반 요청으로 처리한다. 이 요청은 콜백이다.

⑥ Kong 플러그인이 state를 비교하고 Keycloak에 토큰을 요청

  1. 쿠키를 복호화해 state·nonce·PKCE 원본·유효 시각을 꺼낸다.
  2. 쿠키가 없거나 10분이 지났으면 400으로 끝낸다.
  3. 주소에 code·state가 없거나 state가 쿠키와 다르면 400으로 끝낸다.
  4. Keycloak 토큰 주소로 서버끼리 POST한다.
POST https://idp.example.com/realms/product/protocol/openid-connect/token
Authorization: Basic <client_id:client_secret>   # 브라우저는 이 값을 본 적이 없다
grant_type=authorization_code
code=<1회용 코드>
redirect_uri=https://app.example.com/*
code_verifier=<쿠키에 있던 PKCE 원본>           # ②에서 보낸 code_challenge 와 맞아야 한다

→ code가 새도 토큰으로 바꿀 수 없다. client secret은 Kong 플러그인 설정에만, PKCE 원본은 암호화된 쿠키 안에만 있기 때문이다.

→ 쿠키를 지웠거나 로그인에 10분 넘게 걸리면 2번에서 400이 나오고, Kong은 다시 Keycloak으로 보내 주지 않는다. 사용자가 처음 주소를 다시 열어야 한다.

⑦ Keycloak이 ID 토큰을 발급

  1. client secret과 code를 확인한다.
  2. code_verifier의 해시가 ④ 전에 받은 code_challenge와 같은지 확인한다.
  3. ID 토큰·access token·refresh token을 돌려준다.

ID 토큰 안에는 이런 값이 들어 있다(예시).

sub:   3f2a1c…            ← Keycloak 사용자 UUID. 나중에 X-Credential-Identifier 가 된다
email: user@example.com
aud:   app                ← 이 토큰을 받을 client
nonce: 95289df8…          ← ②에서 만든 값 그대로
exp:   발급 + 300초        ← Keycloak access token 수명(기본 300초)

⑧ Kong 플러그인이 ID 토큰을 검증하고 쿠키를 교체

  1. Keycloak 공개키로 서명을 확인하고, aud = app, 만료 전인지, nonce가 쿠키의 nonce와 같은지 확인한다. 실패하면 500이다.
  2. 쿠키를 새로 쓴다.
OIDCSESSION0 = 암호화{ 로그인 완료: true, ID 토큰: "eyJ…" }
  1. 처음 요청했던 주소(/)로 302를 돌려준다.

→ access token과 refresh token은 버린다. 그래서 refresh token으로 세션을 늘리는 기능이 없고, 세션 수명은 3장의 설정이 정한다.

→ 이제 세션의 전부(ID 토큰)가 브라우저 쿠키에 있다. Kong 서버와 Keycloak 서버에는 이 세션의 기록이 없다.

2. API 호출: 쿠키 안 ID 토큰을 사용자 헤더로 바꾸기까지

⑨ 브라우저가 쿠키를 실어 API를 부름

GET https://app.example.com/backend/api/v1/users/me
Cookie: OIDCSESSION0=<암호화{ ID 토큰 }>

→ /와 /backend는 서로 다른 Kong 라우트지만 같은 쿠키를 쓴다. 쿠키 이름이 같고 Path=/이며, 같은 oidcify 프로세스 안에서는 암호화 키도 같다.

⑩ Kong 플러그인이 쿠키를 풀어 ID 토큰을 다시 검증하고 헤더를 붙임

  1. 5분 캐시에서 Keycloak 공개키를 꺼낸다. 캐시가 끝났으면 Keycloak에서 다시 받는다.
  2. 쿠키를 복호화해 ID 토큰의 서명·aud·만료를 확인한다. 이 사용자가 아직 유효한지는 Keycloak에 묻지 않는다.
  3. 통과하면 헤더를 붙여 백엔드로 넘긴다(값은 예시).
X-Consumer-Id:           <consumer UUID>                # 설정의 consumer, 모든 사용자 공통
X-Consumer-Username:     app-oidc
X-Credential-Identifier: 3f2a1c…(Keycloak 사용자 UUID)  # ⑦의 sub
X-User-Email:            user@example.com               # 설정 headers_from_claims {X-User-Email: email}

→ 같은 이름의 헤더가 요청에 이미 있으면 플러그인이 덮어쓰거나 지운다. 그래서 브라우저가 헤더를 직접 넣어도 백엔드에는 플러그인이 넣은 값만 간다.

→ 만료가 지났거나 쿠키를 풀지 못하면 헤더 대신 ②처럼 Keycloak으로 302한다.

⑪ 백엔드가 헤더로 사용자를 확인

→ 백엔드도 쿠키를 받지만 풀 키가 없다. 그래서 X-Credential-Identifier만 보고 사용자를 알고, 백엔드 코드에는 로그인 처리가 없다. 이 글 첫 줄의 3f2a1c…가 여기서 찍힌 값이다.

3. Keycloak 장애·세션 수명·Kong 재시작·로그아웃에서 생기는 결과

①~⑪에서 세션이 브라우저 쿠키에만 있고 Kong이 Keycloak에 사용자를 묻지 않는다는 것을 봤다. 그래서 아래 결과는 Kong 플러그인 설정으로 정해진다.

Keycloak이 멈추면 로그인한 사용자도 5분 안에 500을 받음

  1. ⑩의 서명 확인에 Keycloak 공개키가 필요하다 → Kong은 공개키와 설정 문서를 5분 동안 캐시한다.
  2. 5분이 지나면 다음 요청에서 설정 문서를 Keycloak에서 다시 받는다.
  3. 이때 Keycloak이 응답하지 않는다 → 설정 문서를 받지 못한다.
  4. 쿠키가 멀쩡해도 → 500.

Kong을 거치지 않는 경로가 있으면 헤더를 위조할 수 있음

  1. 백엔드는 ⑪처럼 헤더만 믿는다 → 헤더를 덮어쓰는 것은 ⑩의 Kong 플러그인이다.
  2. Kong을 거치지 않고 백엔드에 닿는 경로가 있다 → 그 경로로 온 요청의 헤더는 덮어써지지 않는다.
  3. 누구나 X-Credential-Identifier, X-User-Email을 직접 넣어 다른 사용자로 요청할 수 있다.

라우트마다 세션 수명이 다르면 가장 짧은 값이 전체 세션을 끊음

  1. ⑨처럼 /와 /backend가 같은 쿠키를 쓴다.
  2. 수명이 짧은 라우트에서 ⑩의 만료 확인이 실패한다 → 그 라우트가 쿠키를 "로그인 진행 중" 상태로 덮어쓴다.
  3. 덮어쓴 쿠키에는 ID 토큰이 없다 → 수명이 긴 라우트의 세션도 함께 끝난다.

session_lifetime_seconds = 0(기본값)이면 5분마다 세션이 끝나고 Keycloak을 거쳐 다시 로그인됨

  1. 만료 = ⑦의 exp = 발급 + 300초(Keycloak 기본값).
  2. refresh token이 없다(⑧) → 5분 뒤 요청은 ⑩에서 만료로 실패한다 → Kong이 Keycloak으로 302한다.
  3. Keycloak 세션이 남아 있다 → ④에서 비밀번호 없이 돌아온다. 이때 Keycloak 세션도 갱신돼 최대 10시간(기본값)까지 간다.
  4. 화면 이동은 Keycloak을 거쳐 같은 화면으로 돌아온다. 하지만 fetch로 부른 API는 Keycloak 주소로 302를 받는다 → 브라우저가 다른 도메인 응답을 막아(CORS) 호출이 실패한다(예상).

→ 고객 현장 배포에서 "5분마다 로그인이 풀린다"는 문의가 있었고, 원인이 이 경우였다.

session_lifetime_seconds = 99999이면 Kong 세션이 Keycloak 세션보다 27시간 넘게 오래 감

  1. 만료 = 발급 시각 + 99999초(약 27.8시간). ⑦의 exp는 보지 않는다 → 5분마다 Keycloak으로 가는 일이 없다.
  2. 브라우저가 로그인 뒤 Keycloak에 다시 가지 않는다 → Keycloak 세션이 갱신되지 않는다.
  3. Keycloak 세션은 유휴 만료(기본 1800초 = 30분)로 먼저 끝난다.
  4. Kong 세션은 그 뒤로 약 27.3시간(99999 − 1800 = 98199초) 더 통과한다.

→ 두 세션(Kong, Keycloak)은 따로 만료되고, 둘을 맞춰 주는 설정은 없다.

어느 설정이든 쿠키 자체에 상한이 둘 있음

  • 쿠키에 만료 속성(Expires)이 없다 → 브라우저를 닫으면 쿠키가 사라진다.
  • 쿠키 라이브러리(gorilla/securecookie)는 기본으로 30일 지난 쿠키를 거부한다 → 설정이 30일보다 길어도 발급 30일 뒤에는 복호화에 실패한다.

쿠키 암호화 키를 비워 두면 Kong 재시작 때 모든 사용자가 다시 로그인함

쿠키를 서명·암호화하는 키는 플러그인 설정 cookie_hash_key_hex, cookie_block_key_hex 두 개다. 비워 두면 플러그인은 프로세스가 시작할 때 무작위 키를 만들어 메모리에만 둔다.

// main.go — 프로세스 시작 때 한 번
autoGenHashKey  = securecookie.GenerateRandomKey(cookieKeyLenBytes)  // cookieKeyLenBytes = 32
autoGenBlockKey = securecookie.GenerateRandomKey(cookieKeyLenBytes)
  1. Kong 파드가 재시작된다 → 플러그인이 새 무작위 키를 만든다. 옛 키는 메모리와 함께 사라졌다.
  2. 브라우저 쿠키는 옛 키로 암호화돼 있다 → ⑩에서 복호화되지 않는다.
  3. 플러그인은 세션이 없는 것으로 본다 → ②와 같은 302를 돌려준다.
  4. 사용자마다 다음 요청에서 다시 로그인한다.

→ 확인한 클러스터에서는 oidcify 설정 9개 중 켜져 있는 7개가 모두 키를 비워 두고 있었다(키가 들어 있는 1개는 꺼져 있음).

Kong 파드가 두 대면 로그인이 풀렸다 붙었다 함

  1. 키를 비워 두면 파드 A와 파드 B가 각자 다른 무작위 키를 갖는다.
  2. 파드 A에서 로그인했다 → 쿠키는 키 A로 암호화돼 있다.
  3. 다음 요청이 파드 B로 간다 → 키 B로 복호화되지 않는다 → 302. ⑤의 콜백이 파드 B로 가면 ⑥의 2번에서 400.

→ 확인한 클러스터는 Kong 파드가 한 대라 이 경우는 생기지 않았다.

쿠키 키는 16진수 64자 두 개를 모든 라우트에 같게 넣음

openssl rand -hex 32   # 한 번에 하나씩, 두 번 실행해 두 키에 넣는다

→ README는 32자라고 적지만 소스의 입력 검사는 len=64다.

→ 같은 도메인의 모든 oidcify 라우트에 같은 두 값을 넣어야 한다. 일부 라우트만 넣으면 라우트를 오갈 때 서로 쿠키를 풀지 못한다.

쿠키 키가 새면 쿠키 안 ID 토큰을 읽고 진짜 토큰으로 쿠키를 다시 만들 수 있음

  1. 키를 아는 사람은 가로챈 쿠키를 풀어 안의 ID 토큰(이메일·사용자 UUID)을 읽을 수 있다.
  2. 플러그인은 ⑩에서 매번 ID 토큰의 Keycloak 서명을 확인한다 → 서명 없는 가짜 토큰으로 쿠키를 만들 수는 없다.
  3. 손에 넣은 진짜 ID 토큰은 새 쿠키로 다시 감쌀 수 있다 → 발급 시각 + session_lifetime_seconds까지 그 사용자로 통과한다. 새로 감쌌으니 쿠키 30일 상한도 다시 시작된다.

→ 그래서 쿠키 키도 client secret처럼 다룬다.

Keycloak에서 사용자를 막아도 이미 받은 쿠키는 만료까지 통과함

  1. Keycloak에서 사용자를 비활성화하거나 역할을 바꾼다.
  2. Kong은 ⑩에서 Keycloak에 사용자를 묻지 않는다 → 이 변경을 모른다.
  3. 이미 발급된 쿠키는 만료까지 그대로 통과한다. session_lifetime_seconds가 0이면 최대 5분, 99999면 최대 약 27.8시간이다(그 전에 브라우저를 닫으면 그때 끝난다).
  4. 백엔드가 Keycloak에 사용자를 따로 조회하지 않는다면, 그동안 백엔드도 요청을 받는다.

→ 특정 사용자 한 명의 세션만 끊는 방법은 없다. 쿠키 키를 바꿔 모든 사람의 세션을 한꺼번에 끊는 방법만 있다.

로그아웃은 Kong 쿠키만 지우고 Keycloak 세션은 남김

GET https://app.example.com/logout       # 설정 logout_path
→ OIDCSESSION 쿠키 삭제
→ 302 location: https://app.example.com/  # 설정 post_logout_redirect_uri. 비워 두면 200 "Logged out" 페이지
  1. /logout은 Kong 쿠키만 지운다 → Keycloak 도메인의 Keycloak 세션 쿠키는 그대로다.
  2. 다시 접속하면 ①~④를 다시 거친다 → ④에서 Keycloak 세션이 아직 만료되지 않았으면 비밀번호 없이 로그인된다.

→ 완전히 로그아웃하려면 브라우저가 Keycloak 로그아웃 주소(https://idp.example.com/realms/product/protocol/openid-connect/logout)로도 이동해야 한다. post_logout_redirect_uri를 그 주소로 두면 두 로그아웃이 한 번에 이어진다.

4. 로그인 문제는 302·Keycloak 응답·세션 수명·Kong 재시작 순서로 확인

  1. 첫 요청에 302 대신 500이 나온다 → ②에서 Kong이 Keycloak 설정 문서를 받지 못했다. Keycloak 주소·인증서를 본다.
  2. 로그인한 사용자가 갑자기 500을 받는다 → ⑩의 5분 캐시가 끝난 시점에 Kong에서 Keycloak으로 연결되지 않았다. 그 시각의 Keycloak 상태를 본다.
  3. 5분마다 또는 예상보다 일찍 로그인이 풀린다 → 그 도메인에 붙은 oidcify 라우트들의 session_lifetime_seconds 중 가장 짧은 값을 본다.
  4. 모든 사용자가 한꺼번에 로그인이 풀렸다 → 그 시각에 Kong 파드가 재시작됐는지와 쿠키 키 설정을 본다.
