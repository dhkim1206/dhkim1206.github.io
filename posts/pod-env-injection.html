파드 환경변수 주입 방식별 우선순위와 값이 조립되는 과정

파드 안 환경변수 값의 출처를 거꾸로 따라가며, 재시작 전 env 고정·없는 secretRef·${VAR} 미치환까지 확인한 기록입니다.

파드 키 불일치envFrom→env 순서배제한 원인값·출처 확인 secretKeyRef 덮어쓰기sed 치환 누락재배포 조치재시작·secretRef·${VAR}확인하지 못한 것맺음말

ConfigMap·GitOps는 정상인데 파드 안 키가 달랐다

데이터 파이프라인을 배포하고 나서, AI 판정 결과를 화면용 알람·지표 값으로 바꾸는 후처리 서비스가 S3 API로 접근하는 Ceph 오브젝트 스토리지(RGW)를 제대로 쓰는지 확인하던 중이었습니다. 이 서비스의 S3 접속 키는 ConfigMap에 들어 있고, 배포 스크립트가 그 키를 고객 현장 클러스터의 RGW 키로 바꿔 넣으면 GitOps 도구가 클러스터에 적용합니다.

그래서 이 경로를 따라 네 곳을 확인했습니다.

ConfigMap현장 키가 들어 있음
배포 스크립트 로그키 주입 완료
GitOps 앱 상태Synced, Healthy
RGW그 키로 유저가 조회됨
예상파드도 이 키를 쓰고 있을 것
실측파드 안 AWS_ACCESS_KEY_ID가 ConfigMap 값과 다르고, RGW에 없는 키

이대로면 S3를 호출하는 순간 InvalidAccessKeyId가 납니다. 같은 템플릿을 쓰는 다른 현장 한 곳에서는 실제로 이 상태 때문에, 후처리 서비스가 판정 결과마다 실행할 스크립트를 정한 라우팅 설정 파일을 S3에서 받지 못해 결과를 만들지 못했습니다.

ConfigMap도 맞고 GitOps도 Synced인데 애플리케이션이 다른 값을 쓰는 상황을 겪어 보셨나요? 이번 원인은 ConfigMap·Secret에 적힌 값이 파드 환경변수로 들어가는 단계에 있었습니다.

kubelet은 envFrom을 먼저 펼치고 env로 덮어쓴다

원인을 찾으려면 먼저 파드에 환경변수가 어떤 경로로 들어오는지 알아야 합니다. 컨테이너 spec에서 환경변수를 넣는 필드는 envFrom과 env 두 개입니다.

containers:
  - name: postprocessing
    envFrom:                         # ConfigMap의 키 전부를 이름 그대로 넣음
      - configMapRef:
          name: app-postprocessing-config
    env:                             # 변수 하나씩, 이름을 직접 정해 넣음
      - name: AWS_ACCESS_KEY_ID
        valueFrom:
          secretKeyRef:
            name: app-postprocessing-secret
            key: accessKey           # Secret의 키 이름은 accessKey

ConfigMap에 AWS_ACCESS_KEY_ID와 LOG_LEVEL(예시) 두 키가 있다면, 이 파드 안에는 다음 환경변수가 생깁니다.

AWS_ACCESS_KEY_ID=<Secret의 accessKey 값>   ← env 값이 envFrom 값을 덮음
LOG_LEVEL=<ConfigMap 값>                    ← envFrom

kubelet은 컨테이너를 띄울 때 envFrom을 목록 순서대로 먼저 펼치고, 그 위에 env를 얹습니다. 이름이 겹치면 나중에 얹은 쪽이 남습니다.

이 순서는 Kubernetes API Reference(v1.32)의 Container.envFrom 설명에 적혀 있습니다.

"When a key exists in multiple sources, the value associated with the last source will take precedence. Values defined by an Env with a duplicate key will take precedence."
kubectl explain pod.spec.containers.envFrom   # 쓰는 클러스터 버전의 같은 설명 확인

kubelet의 makeEnvironmentVariables(pkg/kubelet/kubelet_pods.go, release-1.32)도 container.EnvFrom을 맵에 먼저 넣고 container.Env로 같은 이름을 덮어씁니다.

그래서 ConfigMap이 적용됐다는 것과 파드가 그 값을 쓴다는 것은 다른 일입니다. 파드가 쓰는 값은 ④에서 조립된 목록이라 ①과 ④ 사이의 ②③에서 값이 바뀔 수 있는데, 처음 확인한 네 곳은 모두 ①의 재료만 본 것이었습니다.

배포 스크립트 실패와 키 만료는 원인이 아니었다

출처를 비교하기 전에, 처음 확인한 사실만으로 지울 수 있는 후보부터 지웠습니다.

후보근거판정
배포 스크립트가 키를 못 넣었다ConfigMap에 현장 키가 있고 스크립트 로그도 성공탈락
현장 키가 만료·삭제됐다ConfigMap 키로 RGW 유저가 조회됨탈락

남는 설명은 파드가 ConfigMap이 바뀌기 전에 떠서 옛 값을 들고 있는 경우와, ConfigMap이 아닌 다른 곳에서 키를 받는 경우 둘입니다.

ConfigMap·Secret·파드 안 값을 비교하고 출처는 describe로 확인한다

ConfigMap·Secret·파드 안 세 곳에서 같은 키의 값을 꺼내 비교했습니다.

# ConfigMap 값
kubectl get cm app-postprocessing-config -o yaml | grep AWS_ACCESS_KEY_ID
# Secret 값
kubectl get secret app-postprocessing-secret -o jsonpath='{.data.accessKey}' | base64 -d
# 파드 안 값
kubectl exec deploy/app-postprocessing -- env | grep AWS_ACCESS_KEY_ID
# 값이 어디서 들어오는지
kubectl describe deploy app-postprocessing

값이 같다는 것만으로는 어디서 들어왔는지 모릅니다. 출처는 describe 출력의 Environment Variables from(envFrom)과 Environment(env)에서 확인합니다.

문제 현장에서만 env의 secretKeyRef가 ConfigMap 키를 덮었다

기준선으로, 같은 파이프라인이 도는 다른 네 현장의 후처리 서비스 deployment를 확인했습니다. 앞에서 장애를 겪은 현장도 이후 고쳐져 이 네 곳에 들어 있습니다.

envFrom: [{"configMapRef":{"name":"app-postprocessing-config"}}]
env 이름: PYTHONUNBUFFERED PYTHONPATH

env에 ConfigMap 키와 이름이 겹치는 항목이 없어 ①이 그대로 ④가 됩니다. app-postprocessing-secret이 클러스터에 있어도 어떤 필드도 참조하지 않으므로 파드에 들어가지 않습니다.

같은 확인을 문제 현장에서 했습니다. 키 값은 가리고 같은 값끼리 같은 이름으로 적었습니다.

env 이름: AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY PYTHONUNBUFFERED PYTHONPATH
envFrom: [{"configMapRef":{"name":"app-postprocessing-config"}}]
ConfigMap · AWS_ACCESS_KEY_ID값 A
Secret · accessKey값 B
파드 안 · AWS_ACCESS_KEY_ID값 B= Secret 값

env의 AWS_ACCESS_KEY_ID가 secretKeyRef로 Secret의 accessKey를 가리키고 있었습니다. ConfigMap의 정상 키는 ①에서 들어왔다가 ③에서 덮였습니다. env가 envFrom보다 우선하므로 ConfigMap이 언제 바뀌었든 파드 값은 Secret 값이 되고, 옛 값을 들고 있다는 후보도 여기서 탈락합니다.

배포 스크립트가 Secret의 accessKey는 치환하지 않았다

Secret에 현장 키가 아닌 값이 들어 있던 이유는 배포 스크립트의 치환 규칙에 있었습니다.

# ak: 현장 RGW access key, dir: 치환할 매니페스트 디렉토리
ACCESS_VARS="AWS_ACCESS_KEY_ID S3_ACCESS_KEY_ID MODEL_REGISTRY_ACCESS_KEY_ID ..."
for var in $ACCESS_VARS; do
  find "$dir" -type f -exec sed -i "s|${var}: \"[^\"]*\"|${var}: \"${ak}\"|g" {} +
done

스크립트는 정해진 이름의 이름: "값" 줄만 평문으로 바꿉니다. Secret의 키 이름은 accessKey라 목록에 없고, 값도 data: 아래에 base64로 들어 있어 평문 치환 대상이 될 수 없습니다. 그래서 Secret에는 템플릿을 처음 만들 때 넣은 개발 환경 키가 그대로 남았습니다. 정리하면 원인은 세 고리입니다.

  1. 키를 ConfigMap과 Secret 두 군데에 두는 템플릿이 있었습니다.
  2. 배포 스크립트는 ConfigMap의 평문 키만 치환했고, Secret의 base64 키는 치환하지 못했습니다.
  3. deployment의 env가 치환되지 않은 Secret 쪽을 같은 이름으로 다시 넣었습니다.
ConfigMap 경로Secret 경로플랫폼·템플릿 어긋난 지점외부(RGW)결과 정상흐름문제 흐름확인용

env의 AWS_ACCESS_KEY_ID·AWS_SECRET_ACCESS_KEY를 지운 템플릿으로 재배포한다

저장소의 현재 템플릿에서는 후처리 서비스 deployment의 env에 AWS_ACCESS_KEY_ID와 AWS_SECRET_ACCESS_KEY가 이미 없습니다. 문제 현장은 그 수정 전 매니페스트로 배포된 상태였으므로, 조치는 수정된 템플릿으로 다시 배포하는 것입니다. ③에서 덮는 항목이 없어지면 ①의 ConfigMap 값이 그대로 ④가 되고, 같은 파이프라인의 다른 서비스 deployment가 S3 키를 ConfigMap envFrom으로만 받는 방식과도 맞습니다.

배포 스크립트 목록에 accessKey를 추가해 Secret 쪽을 고치는 방법은 쓸 수 없습니다. Secret 값은 base64라 sed로 평문 키를 넣으면 apiserver가 거부하거나 다른 바이트로 저장합니다.

재배포하면 파드가 한 번 롤링 재시작됩니다. Secret 객체는 그대로 남지만 env가 참조하지 않으므로 파드에 들어가지 않습니다.

재시작 전 env 고정, 없는 secretRef, ${VAR}도 매니페스트와 파드 안 값을 가른다

아래 셋도 kubelet이 환경변수를 조립하는 단계에서 매니페스트 값과 파드 안 값이 갈리는 경우입니다.

ConfigMap을 바꿔도 env 값은 컨테이너 재시작 전까지 그대로다

환경변수는 ④ 시점에 고정되므로, ConfigMap을 바꿔도 컨테이너가 다시 시작되기 전까지 파드 안 값은 옛 값입니다. kind로 띄운 Kubernetes v1.37 클러스터에서 ConfigMap 값을 바꾸고 150초씩 3회 지켜봤는데, env와 envFrom으로 넣은 값은 한 번도 바뀌지 않았습니다.

시점ConfigMap파드 안 값
수정 전AA
수정 직후BA
kubectl rollout restart deploy/<이름> 후BB

GitOps 도구가 Synced를 보여 줘도 파드는 A일 수 있으니, ConfigMap만 바뀌는 배포라면 해당 deployment를 재시작해야 합니다. 크래시로 재시작된 컨테이너만 새 값을 가져가 파드마다 값이 섞일 수도 있습니다(kubelet 소스 기준, 재현은 하지 않았습니다).

envFrom.secretRef의 Secret이 없으면 파드가 뜨지 않는다

envFrom.secretRef가 가리키는 Secret이 없으면 kubelet이 envFrom을 펼치는 단계에서 멈추고, 파드는 CreateContainerConfigError로 뜨지 않습니다. 그래서 키 없는 빈 Secret(data: {})을 참조용으로만 두는 구성이 생기는데, 문제 현장의 센서 원신호를 정제하는 전처리 서비스(preprocessing)가 그랬습니다.

빈 Secret 대신 secretRef에 optional: true를 주면 Secret이 없어도 파드가 뜹니다(문서·소스 기준, 재현은 하지 않았습니다). 아래는 예시이고, 이번 현장에는 적용하지 않았습니다.

envFrom:
  - secretRef:
      name: <secret 이름>
      optional: true

빈 Secret을 없앨 때는 secretRef를 먼저 제거하거나 optional: true로 바꾼 뒤 Secret을 지웁니다. Secret만 먼저 지우면 다음 컨테이너 시작 때 위 오류가 나고, GitOps에서는 같은 커밋에 둘 다 지워도 적용 순서가 보장되지 않습니다.

빈 자리를 더미 값으로 채울 때도 주의할 점이 있습니다. data는 base64여야 해서, aaaaa: 'aaaaa'처럼 base64로 해석되지 않는 값은 apiserver가 illegal base64 data at input byte 4로 거부합니다(dry-run 실측). aaaa처럼 해석되는 값은 오류 없이 저장되지만, 파드에는 aaaa가 아니라 그 값을 base64로 디코딩한 바이트가 들어갑니다. 평문은 stringData에 넣으면 apiserver가 data로 합쳐 저장합니다.

${VAR}는 치환되지 않고, $(VAR)로 바꿔도 Dockerfile ENV 값은 참조하지 못한다

env:
  - name: PYTHONPATH
    value: "${PYTHONPATH}:/app"

문제 현장 파드 안에서 꺼낸 값은 ${PYTHONPATH}:/app 문자 그대로였습니다. Kubernetes가 env.value 안에서 치환하는 건 $(VAR) 형식뿐이고, ${VAR}는 셸 문법이라 그대로 들어갑니다. Python은 존재하지 않는 경로를 무시해 동작은 하지만, 의도한 "기존 값 뒤에 붙이기"는 일어나지 않습니다.

$(PYTHONPATH)로 고쳐도 마찬가지입니다. $(VAR)가 참조하는 대상은 컨테이너 spec에서 앞서 정의된 환경변수와, kubelet이 같은 네임스페이스의 Service마다 넣는 FOO_SERVICE_HOST 같은 서비스 환경변수뿐이고, Dockerfile의 ENV는 여기에 들지 않습니다. kind로 띄운 Kubernetes v1.37 클러스터에서 value에 $(PATH):/extra를 넣으면 파드 안 값이 $(PATH):/extra 글자 그대로 남았습니다. 이미지 값 뒤에 붙이려면 그 값을 spec에 직접 적거나(value: "<이미지의 기존 경로>:/app"), 경로 설정을 Dockerfile 쪽으로 옮깁니다.

확인하지 못한 것

  • 문제 현장에는 아직 수정된 템플릿을 반영하지 않았고, 반영 후 파드 안 값도 확인하지 않았습니다.
  • 문제 현장에는 최근 24시간 로그에 인증 오류가 없었는데, S3 호출이 아직 없었기 때문으로 추정했습니다. 같은 로그에 Kafka 컨슈머 그룹을 관리하는 코디네이터를 찾지 못한다는 GroupCoordinatorNotAvailableError가 반복되고 있어, 메시지를 못 받아 S3까지 가지 않았을 가능성이 있지만 확인하지 않았습니다.
  • API 문서·kubelet 소스는 현장 버전(v1.32)으로 인용했고, 재현 실험은 kind 기본값(v1.37)으로 했습니다.
  • 다섯 현장 모두 같은 템플릿 계열이라, 다른 구성에서도 다섯 곳 중 한 곳이라는 비율로 생긴다고 일반화할 근거는 없습니다.

ConfigMap과 Secret에 다른 값을 넣고, envFrom으로 ConfigMap을, env.valueFrom.secretKeyRef로 같은 이름의 Secret 키를 지정한 뒤 printenv로 확인하면 Secret 값이 나옵니다.

맺음말

파드가 쓰는 값은 컨테이너가 시작할 때 조립된 환경변수 목록에서 나옵니다.

GitOps의 Synced는 매니페스트가 클러스터에 적용됐다는 것까지만 알려 줍니다. 이번에 지킨 판단 순서는 이렇습니다.

  1. 소스(ConfigMap·스크립트 로그·GitOps 상태)가 정상인 것을 확인합니다.
  2. 파드 안 실제 값을 꺼내 ConfigMap·Secret 값과 비교합니다.
  3. 일치하는 출처를 찾고, 그 출처를 만든 필드(env·envFrom)를 고칩니다.

설정은 전부 맞는데 파드가 다르게 동작하면, 소스를 다시 보기 전에 파드 안 값의 출처부터 확인하세요.
