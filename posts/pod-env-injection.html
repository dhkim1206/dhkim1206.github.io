ConfigMap의 키는 맞는데 파드는 틀린 키를 쓴다

env가 envFrom을 덮는 지점을, 파드 안 값의 출처부터 거꾸로 추적한 기록입니다.

Kubernetes v1.32Rook-Ceph RGWGitOps 배포2026년 10월 실측
설정은 정상두 경로후보 소거출처 비교 해시 결과원인고친 것함정 세 가지못 본 것맺음말

설정은 전부 정상이었습니다

고객 현장의 폐쇄망 클러스터에 데이터 파이프라인을 배포하고 나서, AI 판정 결과를 화면용 알람·지표 값으로 바꾸는 후처리 서비스(postprocessing)가 오브젝트 스토리지(S3 호환 RGW)를 제대로 쓰는지 확인하던 중이었습니다. 이 서비스는 S3 접속 키를 ConfigMap에서 받습니다. 배포 스크립트가 템플릿에 들어 있던 개발 환경 키를 현장 RGW 키로 바꿔 넣고, GitOps 도구가 클러스터에 적용하는 구조입니다.

먼저 네 곳을 확인했습니다.

ConfigMap 조회AWS_ACCESS_KEY_ID에 현장 키가 들어 있음
배포 스크립트 로그OK inject .../app (AK=…) 주입 완료
GitOps 앱 상태Synced, Healthy
RGW 유저 조회그 키로 user_id: app-pipeline — 현장 RGW에 등록된 유효한 키
예상파드도 ConfigMap의 이 키를 쓰고 있을 것
실측파드 안 printenv AWS_ACCESS_KEY_ID 값이 ConfigMap과 다름. 그 키로 RGW를 조회하면 아무것도 나오지 않아, S3를 호출하는 순간 InvalidAccessKeyId

같은 템플릿을 쓰는 다른 환경에서는 이 상태가 실제 장애로 이어진 적이 있습니다. 후처리 서비스가 판정 결과마다 실행할 스크립트를 정한 라우팅 설정 파일을 S3에서 받지 못해, 판정 결과를 최종 값으로 바꾸지 못했습니다. 이번 현장은 최근 24시간 로그에 인증 오류가 없었는데, S3 호출이 아직 없었기 때문으로 추정합니다.

ConfigMap도 맞고 GitOps도 Synced인데 애플리케이션이 다른 값을 쓰는 상황을 겪어 보셨나요? 이 경우 설정 소스만 다시 봐서는 원인이 나오지 않습니다. 이번 원인은 소스의 값이 파드로 들어가는 단계에 있었습니다. 이 글은 파드 안 값이 어디서 왔는지 거꾸로 찾아간 기록입니다.

측정은 2026년 10월 한 현장 기준이고, 나머지 네 현장은 같은 날 상태만 비교했습니다. 키 값은 노출하지 않고 sha256 앞 8자리로만 비교하며, 리소스·유저 이름은 일반화했습니다.

파드 환경변수는 두 경로로 들어오고, 같은 이름이면 한쪽이 진다

뒤의 추적에서 왜 해시 세 개를 비교하는지 이해하려면, 파드에 환경변수가 들어오는 경로부터 알아야 합니다. 컨테이너 spec에는 환경변수를 넣는 필드가 두 개 있습니다.

필드넣는 방식변수 이름
envFromConfigMap·Secret의 키 전부키 이름 그대로 (prefix를 주면 앞에 붙음)
env변수 하나씩. value 또는 valueFrom(키 하나)지정한 이름 (accessKey 키 → AWS_ACCESS_KEY_ID 변수도 가능)

kubelet은 컨테이너를 띄울 때 envFrom을 목록 순서대로 먼저 펼치고, 그 위에 env를 얹습니다. 이름이 겹치면 나중에 얹은 쪽이 남습니다.

이 우선순위는 Kubernetes가 API 명세로 정의한 동작입니다. Kubernetes API Reference(v1.32)의 Container.envFrom 필드 설명은 다음과 같습니다.

"When a key exists in multiple sources, the value associated with the last source will take precedence. Values defined by an Env with a duplicate key will take precedence."
— Kubernetes API Reference v1.32, Container.envFrom (클러스터에서는 kubectl explain pod.spec.containers.envFrom으로 같은 설명을 볼 수 있습니다)

구현도 명세와 같습니다. kubelet의 makeEnvironmentVariables(pkg/kubelet/kubelet_pods.go, release-1.32)는 container.EnvFrom을 목록 순서대로 돌며 값을 맵에 넣고, 그다음 container.Env를 같은 맵에 다시 써서 같은 이름의 값을 덮어씁니다.

여기서 갈라 둘 것이 있습니다. ConfigMap을 "적용했다"와 파드가 "그 값을 쓴다"는 다른 사건입니다. 적용은 apiserver에 객체가 저장되는 것이고, 파드가 쓰는 값은 ④ 시점에 조립된 목록입니다. 그 사이에 ②③이 끼어들 수 있습니다. ConfigMap 조회, 스크립트 로그, GitOps 상태, RGW 조회까지 처음에 확인한 네 곳은 전부 ①의 재료만 본 것이었습니다.

소스 쪽 후보는 둘 다 탈락했다

파드 값이 ConfigMap과 다르다는 것만으로는 원인이 여럿일 수 있습니다. 출처를 비교하기 전에, 처음 확인한 사실만으로 지울 수 있는 후보부터 지웠습니다.

후보근거판정
배포 스크립트가 키를 못 넣었다ConfigMap에 현장 키가 있고 스크립트 로그도 성공탈락
현장 키가 만료·삭제됐다ConfigMap 키로 RGW를 조회하면 유저가 나옴탈락

남는 설명은 둘입니다. 파드가 ConfigMap이 바뀌기 전에 떠서 옛 값을 들고 있거나, ConfigMap이 아닌 다른 곳에서 키를 받고 있는 경우입니다. 뒤의 해시 비교와 deployment의 env 목록이 이 둘을 가립니다.

비교는 값이 아니라 출처로 한다

키 값을 화면에 띄우면 기록에 남습니다. 그래서 값 대신 해시로, 세 곳을 같은 방식으로 꺼내 비교합니다.

NS=<namespace>
P=$(kubectl -n $NS get pod -o name | grep postprocessing | head -1)
# ① ConfigMap 값
kubectl -n $NS get cm app-postprocessing-config -o jsonpath='{.data.AWS_ACCESS_KEY_ID}' | tr -d '\n' | sha256sum | cut -c1-8
# ② Secret 값
kubectl -n $NS get secret app-postprocessing-secret -o jsonpath='{.data.accessKey}' | base64 -d | tr -d '\n' | sha256sum | cut -c1-8
# ③ 파드 안 값
kubectl -n $NS exec $P -- printenv AWS_ACCESS_KEY_ID | tr -d '\n' | sha256sum | cut -c1-8

세 번째 값이 어느 쪽과 같은지로 후보를 좁히고, 출처는 deployment의 env·envFrom 목록으로 확정합니다. 해시는 어떤 값인지만 알려 주고, 어디서 들어왔는지는 알려 주지 않기 때문입니다. 세 줄 모두 tr -d '\n'을 거치는 것은 원본 값 끝에 개행이 있을 때 같은 값인데 해시가 달라지는 것을 막기 위해서입니다.

정상 현장에는 겹치는 env가 없었고, 문제 현장에는 있었다

먼저 기준선을 잡았습니다. 같은 파이프라인이 도는 다른 네 현장의 후처리 서비스 deployment입니다.

envFrom: [{"configMapRef":{"name":"app-postprocessing-config"}}]
env 이름: PYTHONUNBUFFERED PYTHONPATH

env에 키와 이름이 겹치는 항목이 없어 ①이 그대로 ④가 됩니다. Secret app-postprocessing-secret도 클러스터에 있지만 아무 필드도 참조하지 않아 파드에 들어가지 않습니다.

같은 확인을 문제 현장에서 했습니다(실측).

env 이름: AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY PYTHONUNBUFFERED PYTHONPATH
envFrom: [{"configMapRef":{"name":"app-postprocessing-config"}}]
ConfigMap · AWS_ACCESS_KEY_ID32aa274d
Secret · accessKey9b86897a
파드 안 · AWS_ACCESS_KEY_ID9b86897a= Secret 값

env의 AWS_ACCESS_KEY_ID는 secretKeyRef로 Secret의 accessKey를 가리킵니다. ConfigMap의 정상 키는 ①에서 들어왔다가 ③에서 덮였습니다. env가 envFrom보다 우선하므로 ConfigMap이 언제 바뀌었든 파드 값은 Secret 값이 됩니다. 파드가 옛 값을 들고 있다는 후보는 여기서 함께 탈락합니다. RGW 조회도 이 흐름과 맞습니다. Secret 키는 조회 결과가 없고, ConfigMap 키는 app-pipeline 유저가 나옵니다.

치환 스크립트는 Secret 쪽 키 이름을 몰랐다

그러면 Secret에는 왜 현장 키가 아닌 값이 들어 있었을까요. 배포 스크립트의 치환 규칙을 보면 답이 나옵니다.

ACCESS_VARS="AWS_ACCESS_KEY_ID S3_ACCESS_KEY_ID MODEL_REGISTRY_ACCESS_KEY_ID ..."
for var in $ACCESS_VARS; do
  find "$dir" -type f -exec sed -i "s|${var}: \"[^\"]*\"|${var}: \"${ak}\"|g" {} +
done

스크립트는 정해진 이름의 이름: "값" 줄만 바꿉니다. Secret의 키 이름은 accessKey라 목록에 없습니다. 그래서 Secret에는 템플릿을 처음 만들 때 넣은 개발 환경 키가 그대로 남았고, env가 그 키를 이름만 AWS_ACCESS_KEY_ID로 바꿔 가져와 ConfigMap 값을 덮었습니다. 원인은 세 고리입니다.

  1. 키를 ConfigMap과 Secret 두 군데에 두는 템플릿이 있었습니다.
  2. 배포 스크립트는 ConfigMap 쪽 이름만 치환했습니다.
  3. deployment의 env가 치환되지 않은 Secret 쪽을 같은 이름으로 다시 넣었습니다.
ConfigMap 경로Secret 경로플랫폼 어긋난 지점외부(RGW)흐름문제 흐름확인용

세 고리는 각각 따로 보면 정상이라, 처음 네 곳을 확인했을 때 모두 통과했습니다.

고친 것: env 두 줄을 지웠다

env에서 AWS_ACCESS_KEY_ID와 AWS_SECRET_ACCESS_KEY를 지웠습니다. ③이 사라지면 ①의 ConfigMap 값이 그대로 ④가 됩니다. 다른 서비스들이 이미 쓰는 "키는 ConfigMap에서" 규칙과도 맞습니다.

반대로 배포 스크립트 목록에 accessKey를 추가해 Secret 쪽을 고치는 방법도 있었습니다. 버린 이유는 같은 키를 두 곳에 두는 구조가 그대로 남기 때문입니다. 다음에 또 한쪽만 바뀌면 같은 일이 생깁니다. 키가 들어오는 길을 하나로 만드는 쪽을 골랐습니다.

이 변경은 deployment 템플릿을 바꾸므로 반영할 때 파드가 한 번 롤링 재시작됩니다. Secret 객체는 GitOps prune이 꺼져 있어 클러스터에 남지만, 참조하는 곳이 없어 영향은 없습니다.

같은 지점에서 생기는 함정 세 가지

"소스는 정상인데 파드 값이 다르다"를 만드는 경우를 셋 더 정리했습니다. 셋 다 매니페스트 값은 맞는데 파드 안 값이 다른 경우입니다. 직접 측정한 것과 문서로만 확인한 것은 문장마다 표기합니다.

ConfigMap을 고쳐도 떠 있는 파드는 옛 값이다

환경변수는 ④ 시점에 고정됩니다. ConfigMap을 바꿔도 컨테이너가 다시 시작되기 전까지 파드 안 값은 옛 값입니다. 크래시로 재시작된 컨테이너만 새 값을 가져가므로 같은 deployment 안에서 파드마다 값이 섞일 수도 있습니다(kubelet 소스 기준, 재현은 하지 않았습니다).

시점ConfigMap파드 안 값
수정 전AA
수정 직후BA
kubectl rollout restart deploy/<이름> 후BB

GitOps 도구가 Synced를 보여 줘도 파드는 A일 수 있습니다. ConfigMap만 바뀌는 배포라면 해당 deployment를 재시작해야 합니다.

secretRef 대상은 기본값으로는 존재해야 한다

envFrom.secretRef가 가리키는 Secret이 없으면 kubelet이 envFrom을 펼치는 단계에서 멈추고, 파드는 CreateContainerConfigError로 뜨지 않습니다. 그래서 키 없는 빈 Secret(data: {})을 참조용으로만 두는 구성이 생깁니다. 문제 현장의 센서 원신호를 정제하는 전처리 서비스(preprocessing)가 그랬고, 다섯 현장 모두 이 Secret의 키가 0개였습니다.

빈 Secret은 필요 없습니다. secretRef에 optional: true를 주면 Secret이 없어도 파드가 뜹니다(문서·소스 기준, 재현은 하지 않았습니다). 아래는 예시이고, 이번 현장에는 적용하지 않았습니다.

envFrom:
  - secretRef:
      name: <secret 이름>
      optional: true

참조를 정리할 때는 secretRef를 먼저 제거하거나 optional: true로 바꾼 뒤 Secret을 지웁니다. Secret만 먼저 지우면 다음 컨테이너 시작 때 위 오류가 납니다. GitOps에서는 같은 커밋에 둘 다 지워도 적용 순서가 보장되지 않습니다.

data에 aaaaa: 'aaaaa' 같은 더미 값을 넣으면, base64로 해석되지 않는 값은 apiserver가 illegal base64 data at input byte 4로 거부합니다(dry-run 실측). 반대로 aaaa처럼 해석되는 문자열은 거부되지 않고 디코딩된 바이트로 오류 없이 저장됩니다. 평문은 stringData에 넣습니다. apiserver가 받아서 data로 합쳐 저장합니다.

${VAR}는 치환되지 않고, $(VAR)로 바꿔도 이미지 값은 못 붙인다

env:
  - name: PYTHONPATH
    value: "${PYTHONPATH}:/app"

파드 안에서 꺼낸 실제 값은 ${PYTHONPATH}:/app 문자 그대로였습니다. Kubernetes가 env.value 안에서 치환하는 건 $(VAR) 형식뿐이고, ${VAR}는 셸 문법이라 그대로 들어갑니다. Python은 존재하지 않는 경로를 무시하고 /app만 써서 동작은 하지만, 작성자가 의도한 "기존 값 뒤에 붙이기"는 일어나지 않습니다.

$(PYTHONPATH)로 고쳐도 의도대로 되지는 않습니다. API 설명상 $(VAR)가 참조하는 대상은 컨테이너에서 앞서 정의된 환경변수와 서비스 환경변수이고, 찾지 못하면 문자열을 그대로 둡니다. 이미지 Dockerfile의 ENV PYTHONPATH는 이 대상에 들지 않습니다(kind v1.37 클러스터에서 $(PATH):/extra가 글자 그대로 남는 것을 확인했습니다). 이미지 값 뒤에 붙이고 싶다면 그 값을 spec에 직접 적거나(value: "<이미지의 기존 경로>:/app"), 경로 설정을 이미지 Dockerfile 쪽으로 옮깁니다.

이 추적이 못 본 것

  • 문제 현장에서 인증 오류가 0건인 이유를 "S3 호출이 아직 없어서"로 봤는데, 이건 추정입니다. 같은 로그에 컨슈머 그룹 코디네이터 오류(GroupCoordinatorNotAvailableError)가 반복되고 있어, 메시지를 못 받아 S3까지 가지 않았을 가능성이 있습니다.
  • 애플리케이션이 accessKey 같은 다른 이름의 변수를 읽는지는 코드로 확인하지 않았습니다.
  • 다섯 현장 모두 같은 템플릿 계열입니다. 다른 구성에서도 같은 비율로 생긴다고 일반화할 근거는 없습니다.

재현은 간단합니다. ConfigMap과 Secret에 다른 값을 넣고, envFrom으로 ConfigMap을, env.valueFrom.secretKeyRef로 같은 이름의 Secret 키를 지정한 뒤 printenv로 확인하면 Secret 값이 나옵니다.

맺음말

파드가 쓰는 값은 컨테이너가 시작할 때 조립된 환경변수 목록에서 나옵니다.

이번에 지킨 판단 순서는 이렇습니다.

  1. 소스(ConfigMap·스크립트 로그·GitOps 상태)가 정상인 것을 확인합니다.
  2. 파드 안 실제 값을 같은 방식으로 꺼내 소스와 비교합니다. 값 대신 해시로 비교합니다.
  3. 일치하는 출처를 찾고, 그 출처를 만든 필드(env·envFrom)를 고칩니다.

설정은 전부 맞는데 파드가 다르게 동작하면, 소스를 다시 보기 전에 파드 안 값의 출처부터 확인하세요.
